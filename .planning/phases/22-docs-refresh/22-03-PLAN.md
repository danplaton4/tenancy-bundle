    **Required structural elements** (Claude has discretion on exact prose; non-negotiable H2 sections + key content below):

    1. **H1: `# Mailer Bootstrapper`**

    2. **Intro paragraph(s)**: One-line summary — "Per-tenant SMTP transport with per-tenant From / Reply-To headers, correct under both synchronous Mailer dispatch and Messenger-routed async dispatch." Cross-link to `getting-started.md#per-tenant-mailer-config` (which Plan 05 creates).

    3. **H2: `## How it works`** — explain the bootstrapper lifecycle in 2-3 paragraphs:
       - `MailerBootstrapper` implements `TenantBootstrapperInterface`; optional dep on `symfony/mailer` (guarded by `interface_exists(\Symfony\Component\Mailer\MailerInterface::class)`)
       - When a tenant is resolved, the bootstrapper provisions a per-tenant SMTP transport keyed on the tenant's `mailerDsn`. The transport is cached in an LRU (default 100 entries) and reused across requests for long-running workers.
       - `TenantMessageDecorator` listens on `MessageEvent` and stamps `X-Transport: tenant_<slug>` BEFORE Messenger serialization. The multi-transport Mailer config routes envelopes to per-tenant `tenant_<slug>` transports.
       - On `TenantContextCleared`, the per-tenant transport cache entries for that tenant are evicted to prevent socket leaks in long-running workers.

    4. **H2: `## Configuring per-tenant SMTP`** — covers part (a) of D-14:
       - Three nullable columns on the Tenant entity: `mailerDsn`, `mailerFrom`, `mailerReplyTo`. Show as a Doctrine attribute snippet (with the optional-Doctrine guard reminder per CLAUDE.md conventions).
       - The `TenantMailerConfigTrait` shortcut — `use TenantMailerConfigTrait;` in a custom Tenant entity provides all three getters and the columns. Reference: `src/Mailer/TenantMailerConfigTrait.php`.
       - Alternative: implement `TenantInterface::getMailerDsn(): ?string`, `getMailerFrom(): ?string`, `getMailerReplyTo(): ?string` manually if the user has a custom mapping that conflicts with the trait. Link to the migration recipe section.

    5. **H2: `## The X-Transport strategy`** — covers part (b) of D-14:
       - Why this strategy: a `From` header alone doesn't pick the SMTP transport in Mailer. The transport is selected from the `X-Transport` header BEFORE Messenger serialization, ensuring async-routed messages remember which tenant's transport to use after the worker dequeues them.
       - Code reference: `TenantMessageDecorator::onMessage()` stamps the header. Multi-transport `mailer.yaml` config keys envelopes to `tenant_<slug>` transports.
       - This is sync-safe AND async-safe — same code path for both.

    6. **H2: `## Async failure-mode warning`** — covers part (c) of D-14 — this is the headline operational caveat:
       - When Mailer is routed async via Messenger and a worker dequeues a message stamped `X-Transport: tenant_acme`, but `acme` has since been deleted from the landlord DB, the message MUST throw — not silently drop.
       - `MailerTransportContractPass` enforces this contract at container compile time. Specifically: if the mailer bootstrapper is enabled but no transport strategy is configured, container compilation fails. If Mailer is routed async via Messenger but the strategy is not `x_transport`, container compilation fails. Reference the compile-time guard by name.
       - Operational implication: monitor your DLQ for `TenantSanitizedTransportException` (from `src/Mailer/Exception/TenantSanitizedTransportException.php`) and alert your team. These represent messages dispatched in one tenant context that failed to send in the worker context — usually because the tenant was deleted or had its DSN changed mid-flight. The DSN credential is redacted from the exception trace per BOOT-04 acceptance.

    7. **H2: `## Migration recipe (existing projects with a custom Tenant entity)`** — covers part (d) of D-14:
       - If the project upgraded from v0.2 → v0.3 and has a custom Tenant entity, point them at `UPGRADE.md`'s "0.2 to 0.3" section for the trait migration. Do NOT duplicate the ALTER TABLE snippet or the trait-import recipe here.
