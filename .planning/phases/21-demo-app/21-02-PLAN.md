<deviations_from_context>
**Replaces non-existent APIs from CONTEXT.md D-05 and D-06** (per RESEARCH §"Critical Discrepancy" Option 1):

1. CONTEXT D-05 says "bin/console tenancy:migrate --create-dbs". The bundle has NO `--create-dbs` flag (verified: src/Command/TenantMigrateCommand.php has only `--tenant`; `grep -rn "create-dbs" src/` returns nothing). This plan introduces a demo-local `App\Command\SeedDemoCommand` (~80 LOC) that:
   - opens a root-credential DBAL connection (NOT the runtime `tenancy` user — the runtime user lacks `CREATE DATABASE` per PATTERNS analog `hype/tests/symfony74-demo/src/Command/SeedTenantsCommand.php` lines 36-43)
   - issues `CREATE DATABASE IF NOT EXISTS tenant_<slug>` for each demo tenant
   - for each tenant: `$tenantContext->setTenant($tenant); $bootstrapperChain->boot($tenant); try { SchemaTool->createSchema(Post metadata); persist seed Posts; flush; } finally { $tenantContext->clear(); $bootstrapperChain->clear(); }`
   - idempotent on re-run (CREATE IF NOT EXISTS + SchemaTool->updateSchema or guarded create)
   - Plan 03's entrypoint runs this BEFORE `exec frankenphp …` (RESEARCH §Pitfall 5 — healthcheck-vs-seed race)

2. D-06: CONTEXT D-06 says "TenantContextOrchestrator::executeAs($tenant, fn() => ...)". This method does NOT exist on `TenantContextOrchestrator` (verified by reading src/EventListener/TenantContextOrchestrator.php). The actual primitive is the explicit setTenant/boot/clear pattern from `TenantMigrateCommand` lines 97-108. `SeedDemoCommand` uses that pattern verbatim — preserving D-06's INTENT (idiomatic PHP fixtures replayable on volume wipe via the bundle's own write path) while replacing the non-existent API. The `LandlordTenantsFixture` (which only touches the landlord DB) does NOT need the boot/clear primitive — it uses the default fixtures-bundle path (`doctrine:fixtures:load --em=landlord`), but in practice we INVOKE it from `SeedDemoCommand` programmatically rather than running `doctrine:fixtures:load` in the entrypoint, because the fixtures bundle's per-EM CLI is finicky with our two-EM split. The seed command is the single canonical entry point.

3. `brandColor` lives on `App\Entity\Landlord\DemoTenant` (subclass), NOT on the bundle's Tenant entity. The subclass maps to the SAME table (`#[ORM\Table(name: 'tenancy_tenants')]`) so we don't introduce STI. RESEARCH §"Open Questions §1" + PATTERNS §"DemoTenant" both endorse this.
</deviations_from_context>
