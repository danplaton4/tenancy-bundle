<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| bootstrapper exception -> response body | An exception raised inside a probe may carry a DSN/credential in its message; that message becomes an `output` field in an unauthenticated health response. This layer builds the sanitizer that scrubs it. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-33-04 | Information Disclosure | HealthResponseSanitizer / BootstrapperHealthResult.output | mitigate | Sanitizer reuses `DsnSanitizer::REDACTION_REGEX` to redact any `scheme://user:pass@host` before serialization; unit test asserts a mysql DSN password is replaced with `***`. Downstream response builders (plans 03/04) MUST run every output string through `sanitize()`/`sanitizeArray()`. |
| T-33-CONTRACT | Tampering | HealthCheckBootstrapperInterface | accept | Sibling interface adds no privileged surface; `check()` is read-only by contract. No existing bootstrapper is forced to implement it (no BC break). Low risk. |

No npm/pip/cargo installs in this plan — package-legitimacy gate not applicable.
</threat_model>
