<objective>
Ship two LogicException subclasses that downstream waves will throw: `MissingFilesystemConfigException` (per_tenant_adapter mode + tenant lacks `adapter_dsn`) and `UnsupportedAdapterDsnSchemeException` (`AdapterDsnParser` encounters a scheme it does not recognise). Both extend `\LogicException` so Symfony Messenger's default retry strategy excludes them — misconfigured tenants do not retry forever (matches the Phase 23 WR-01 invariant for `MissingTenantProviderException`).

Per RESEARCH.md Open Question Q3 (recommendation adopted): a sibling exception class is preferred over reusing `MissingFilesystemConfigException` for the unknown-scheme case — the two failures have different remediation paths (set the column vs add a scheme to the parser) and a sibling exception keeps that distinction observable.

Output: 2 new exception classes + 2 unit tests that pin ancestry. After this plan, Plan 24-04 and Plan 24-06 can throw these exceptions without forward-references.
</objective>
